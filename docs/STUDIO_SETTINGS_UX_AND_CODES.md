## 1. 설정 화면에서 확인할 내용

PC에서 `/studio-control`을 열고 관리자 비밀번호로 로그인한다. 고객 화면에는 관리자 메뉴가 없다. 화면 너비 1,024px 미만에서는 PC 안내만 표시한다.

| 메뉴 | 먼저 입력할 내용 | 실제 반영 위치 |
|---|---|---|
| 업체정보 | 표시명, 대표 이름·전화·이메일, 홈페이지, 로고·직인 | 고객 화면, 검토, PDF, 이메일 |
| 상품 | 상품명, 가격, 설명, 촬영 범위, 원본·보정본 수량, 앨범, 포함 항목, 활성 | 고객 상품 선택, 금액, 계약서·이메일 |
| 옵션 | 옵션명, 추가금액, 설명, 활성 | 옵션 선택과 계약 금액 |
| 할인 / 혜택 | 즉시 할인·추후 Cashback, 코드별 금액·활성 | 할인 선택, 서버 가격 계산, 검토·계약서·이메일 |
| 계약정책 | 계약금, 납부·취소·환불·납품·보관 기준 | 약관과 확정 계약 |
| 고객 입력폼 | 사용 여부, 필수 여부, 표시 문구, 입력 예시 | 고객 입력칸·필수 검사 |
| 계약서 / 안내 문구 | 상품 소개·촬영 범위·후기 안내 등 | 각 기존 안내 영역 |

메뉴 상단에서 용도·반영 위치·예시를 확인한다. 입력칸 아래 설명과 예시는 안내용이며 자동 저장되는 값이 아니다. 가격은 숫자로 입력하며 아래에 `1,250,000원 · 125만원`처럼 표시된다. 상품·고객 입력칸·색상·업체 정보·이미지에는 표시 예시가 있다.

고급 설정에는 짧은 상품명, 상세 안내 문구, 표시 순서, 색상 팔레트 등 드물게 수정하는 값을 모았다. 내부 ID·업체 ID·계약번호 앞글자·폴더 표시명·할인 조건 유형은 읽기 전용이다. 업체 ID와 실제 Drive 폴더 연결을 화면에서 바꾸지 않는다. 대표 이메일 수정은 **신규 접수의 수신자**를 바꾸며 Gmail 발신 계정은 바뀌지 않는다. 사업자정보는 저장할 수 있지만 현재 PDF에 별도 표시 영역을 추가하지 않는다.

상품의 제공 수량·포함 항목·고급 구성 문구는 실제 판매정책에 맞춰 함께 확인한다. 한 입력칸의 수정으로 모든 자유 문구를 자동으로 바꾸지는 않는다.

## 2. 저장과 이력 복구

1. 필요한 값을 수정한다. 아직 고객에게 적용되지 않는다.
2. `저장 전 검증`으로 필수 정보·금액·코드 형식을 확인한다.
3. `전체 변경 저장`을 누르면 이전 값 → 새 값과 사용 여부 변경을 사람이 읽을 수 있는 문장으로 표시한다.
4. `돌아가서 수정`은 저장하지 않는다. `변경사항 저장`은 현재 이력 번호를 기준으로 전체 설정을 한 revision으로 저장한다.
5. 서버 저장과 재조회가 완료된 뒤 성공 메시지를 확인한다.

다른 창에서 먼저 저장했다면 덮어쓰지 않고 충돌로 중단한다. 응답을 확인하지 못했다면 `다시 불러오기`로 현재 이력과 값을 먼저 확인한다. 반복 저장으로 복구하지 않는다.

`이전 설정 복구`는 최근 20개 이력에서 선택한 문서를 새 revision으로 저장한다. 과거 이력을 삭제하거나 번호를 되돌리지 않는다. 복구 시 상품·코드 목록과 활성 여부도 해당 이력으로 돌아간다. 복구 전에 현재 등록 코드와 미처리 계약을 확인한다. 코드 항목이 없던 과거 7개 메뉴 문서도 읽고 복구할 수 있으며 새 revision에는 빈 코드 목록을 추가한다.

## 3. 할인코드 등록·수정·사용 중지

`할인 / 혜택 → 짝꿍 할인코드 → 할인코드 추가`를 선택한다.

- **코드:** 업체가 고객에게 안내할 문자열. 2~64자의 한글·영문·숫자·하이픈·밑줄을 사용한다.
- **코드 할인금액:** 0보다 큰 정수 원화. 예를 들어 30,000원 코드와 75,000원 코드를 함께 등록할 수 있다.
- **활성:** 신규 사용을 허용할지 결정한다. 추가 직후에는 사용 안 함이며 내용을 확인한 뒤 활성으로 바꾼다.
- **내부 ID:** 자동 생성되는 고정 번호. 직접 수정하지 않는다.

비교 정책은 **앞뒤 공백 제거 → Unicode NFC 정규화 → 대문자 변환**이다. `pair-2027`과 ` PAIR-2027 `은 같은 코드다. `PAIR 2027`처럼 내부 공백이 있는 값은 허용하지 않는다. 대소문자만 다른 중복 코드도 저장하지 않는다. 비활성 코드와 같은 이름을 새로 등록하지 말고 기존 항목을 수정한다.

사용 중지할 코드는 활성 체크를 해제한다. 일반 저장에서 기존 코드의 물리 삭제를 차단하며 이력에는 당시 값이 남는다. 짝꿍 혜택 자체를 사용 안 함으로 바꾸면 모든 코드가 중지된다. 고급 설정의 예전 짝꿍 기본금액은 기존 계약·가격 호출과의 호환용 읽기 전용 값이다. **새 계약에는 코드별 확인 금액을 사용한다.**

## 4. 서버 검증과 가격 계산

비공개 설정 문서의 구조:

```ts
type PartnerDiscountCode = {
  id: string;      // 자동 생성되는 고정 내부 번호
  code: string;    // 정규화된 코드
  amount: number;  // 즉시 할인금액, 양의 정수 원
  active: boolean;
};
// StudioSettings.partnerCodes: PartnerDiscountCode[]
// 기존 7개 공개 설정 메뉴와 함께 하나의 immutable revision에 저장
```

고객 페이지에는 공개 업체·상품·약관·폼 설정만 전달한다. 할인코드 전체 목록은 전달하지 않는다. 관리자 API는 인증된 관리자에게만 목록을 반환한다.

고객이 코드를 입력하면 `/api/validate-partner-code`에 입력한 코드와 화면의 설정 binding을 보낸다. 서버는 현재 revision의 활성 코드와 비교해 해당 코드의 유효 여부와 할인금액만 반환한다. 등록되지 않았거나 비활성인 코드는 0원이다. 서버 연결 실패·설정 손상 시 할인 성공으로 처리하지 않는다. 이전 입력의 늦은 응답은 무시하며 새 입력의 결과만 반영한다.

고객 제출과 대표 최종 확정에서도 서버가 다시 확인한다. 고객이 JSON의 할인금액을 바꿔 보내도 무시하고 현재 서버 등록 금액으로 재계산한다. GAS는 저장 Lock 내부에서 revision/hash와 적용 코드·할인 내역을 다시 확인한다. 가격 계산은 기존 `calculateContractPrice` 한 곳에서 수행한다. 후기 Cashback은 계약 총액을 줄이지 않는다.

## 5. 기존 계약과 기존 Sheets의 전환

확정 Snapshot에는 사용 코드와 확인 할인금액을 `data.partnerName`, `data.partnerDiscountAmount`, `pricing.breakdown`에 보존한다. 필드명 `partnerName`은 기존 payload와의 호환을 위해 유지하며 새 계약에서는 정규화한 코드다. 사용한 코드만 기록하며 다른 코드 목록은 계약에 저장하지 않는다. PDF와 고객·대표 이메일은 이 Snapshot을 사용한다.

코드 금액 수정·비활성·설정 복구는 **확정된 계약 금액을 변경하지 않는다.** 이미 발송한 계약 재발송은 기존 중복 방지 규칙으로 차단한다. 미처리 계약은 revision 변경 보호 때문에 검토·확정·발송이 차단될 수 있으므로 정책 변경 전에 처리하거나 별도로 확인해야 한다. 기존 계약을 자동 재승인하거나 마이그레이션하지 않는다.

새 버전은 `PARTNER_SPREADSHEET_ID`, `PARTNER_SHEET_NAME`과 SpreadsheetApp 조회를 사용하지 않는다. 기존 Sheets 데이터나 Script Properties를 자동 삭제하지 않으며 코드 목록을 자동 가져오지도 않는다. 해당 업체의 기존 코드가 필요하면 운영자가 확인한 뒤 관리자 설정에 등록한다. 앱과 `Code.gs` 배포 버전을 함께 갱신해야 한다.

이미 저장해 둔 할인 설명에 고정 금액이나 `짝꿍 성함 확인` 문구가 있다면 관리자에서 코드 검증 안내로 수정한다. 기존 revision의 문구를 자동 덮어쓰지 않는다. 신규 Dear Memory 기본 설정의 설명은 코드 검증 안내로 바꿨으며 과거 계약용 `legacy-v1` 설정은 보존한다.

## 6. 검증 범위

```text
npm run test:settings
npm run test:discount-codes
npm run test:settings-browser
npm test
```

서버 테스트는 실제 API와 Code.gs를 실행하고 Google 입출력만 격리한다. 관리자 브라우저 테스트는 실제 Next 화면/API와 로컬 Demo 저장소를 사용한다. 실제 Gmail 수신·GAS 권한·Drive ACL·물리 모바일 검증은 별도 업체 staging 절차가 필요하다. 이 작업에서 운영 배포나 실제 고객 이메일을 실행하지 않는다.
